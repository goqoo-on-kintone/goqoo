# 再設計セッション 2026-02-24

## 基本方針

### パッケージ分割
現在の「全部入り」構成を以下の3パッケージに分割する。

```
@goqoo/create        # scaffold（npx goqoo new）
@goqoo/vite-plugin   # ビルド設定（Viteプラグイン）
@goqoo/lib        # ランタイムライブラリ（alerts / goqoo() / tools）
```

### ビルドツール
- webpack → **Vite** に移行
- 複数エントリポイントは `rollupOptions.input` で対応済み（Vite v3.2以降）
- React/VueはVite標準対応のため、goqoo側での同梱を廃止

### ダイアログライブラリ
- sweetalert（v1系・メンテ停止）→ **SweetAlert2** に移行
- `confirmDialog` / `successDialog` / `errorDialog` のAPIは維持
- 内部実装のみ書き直し

### goqoo() 関数の責務分離 ✅
- `goqoo()`本体は**二重実行防止のみ**に責務を絞る
- ビルド情報（COMMIT_HASH / BUILT_AT / NODE_ENV）の`window.__devinfo__`への埋め込みは
  `@goqoo/vite-plugin`側の責務に移管する
- これにより `@goqoo/lib` がビルドツール非依存になる

  - 「gyumaを使いますか？」
- 選択した場合のみインストールされる（現行のReact/Vue選択と同じUX）

## 追記：generator系コマンドの扱い

### 廃止するもの
- `goqoo g app`
- `goqoo g customize-view`
- `goqoo g dts`

`g app` / `g customize-view` はAIが代替できるため廃止。
`g dts` はtrunks（スタンドアロンツール）と機能重複のため廃止。

### trunksの位置づけ
ginue・gyumaと同列に、`@goqoo/create` scaffold時の選択肢として追加する。

```
? Frontend Framework › None / React / Vue
? ginueを使いますか？ › Y/n
? gyumaを使いますか？ › Y/n
? trunksを使いますか？ › Y/n
```

### AIバイブコーディング対応
`g app`等のコードジェネレーターの役割をAIに委譲する方針とする。
scaffold時に `CLAUDE.md`（AIコンテキストファイル）を生成し、以下を記載する：

- プロジェクト構造の説明（`src/apps/`配下の規約など）
- `goqoo()`関数の使い方と意図
- kintoneイベントの書き方パターン
- `@goqoo/lib` のダイアログAPIの使い方

「コードを生成する」から「AIがコードを生成できるようコンテキストを提供する」への役割転換。

## 追記：リポジトリ構成（仮決定）

### モノレポ採用（pnpm workspaces）
現リポジトリ（goqoo-on-kintone/goqoo）をそのままモノレポとして再構成する。

```
goqoo/
├── packages/
│   ├── create/        # @goqoo/create（テンプレートも同梱）
│   ├── vite-plugin/   # @goqoo/vite-plugin
│   └── client/        # @goqoo/lib
├── pnpm-workspace.yaml
└── .changeset/
```

### 採用理由
- `workspace:*` プロトコルでパッケージ間参照がシンプル
- Changesets と組み合わせてバージョン管理・CHANGELOG生成を自動化（一人メンテでも効果大）
- `@goqoo/templates` の独立リポジトリを廃止し、`packages/create/templates/` に統合できる

### 廃止されるリポジトリ
- goqoo-on-kintone/goqoo-templates（`@goqoo/templates`）→ `@goqoo/create` に統合

## 追記：kintoneへのJSアップロード設計

### goqoo ↔ gyuma の依存を完全に切る

現行の `g dts` でのみgyumaに依存していたが、`g dts`廃止により依存がゼロになる。
さらにJSアップロード機能も、goqoo本体がgyumaに依存する必要がない設計で実現できる。

### アップロードのフロー

```
vite build → dist/*.js 生成
↓
@kintone/customize-uploader でアップロード
（OAuth認証の場合はgyumaでトークン取得して環境変数経由で渡す）
```

### OAuth認証時のコマンドパターン

```bash
KINTONE_OAUTH_TOKEN=$(gyuma --domain xxx.cybozu.com \
  --scope k:app_settings:read k:app_settings:write k:file:write) \
kintone-customize-uploader customize-manifest.json
```

`@kintone/customize-uploader` は `--oauth-token` オプションおよび
`KINTONE_OAUTH_TOKEN` 環境変数に対応しているため、
gyumaの出力をそのまま渡せる。

### @goqoo/create のscaffold成果物への追加

- `@kintone/customize-uploader` を devDependencies に追加
- `customize-manifest.json` のテンプレートを生成
- `package.json` の scripts に `upload` コマンドを追加
  - パスワード認証版とOAuth認証版を用意（コメントで選択できるように）
- CLAUDE.md にアップロード手順を記載

### goqoo本体の役割

scaffoldが生成したスクリプトとCLAUDE.mdに書くだけ。
goqoo自体はkintone APIを一切叩かない。

## 追記：goqoo メタパッケージ化

### 方針
`goqoo` パッケージ名をRailsのような「メタパッケージ」として再定義する。

```bash
npm install goqoo
# 内部的に以下が全部入る
# @goqoo/create
# @goqoo/vite-plugin
# @goqoo/lib
```

### goqoo/package.json（イメージ）
```json
{
  "name": "goqoo",
  "dependencies": {
    "@goqoo/create": "latest",
    "@goqoo/vite-plugin": "latest",
    "@goqoo/lib": "latest"
  }
}
```

### ポイント
- goqoo本体にはロジックを書かない（依存を束ねるだけ）
- 既存の `goqoo` パッケージ名をそのまま再利用できる
- ユーザーは `goqoo` という名前さえ知っていれば良い
- 各サブパッケージはChangesetsで独立管理、メタパッケージが最新を束ねる
